# COMPATIBILITY — совместимость форматов

## Профили

Rust-реестр читает исходные JSON-файлы из `profiles/` без конверсии.
Поддерживаются оба расположения: плоский каталог оригинала и дополнительные
`profiles/apache/`, `profiles/fpm/`. Файлы `schema.json`, `fpm-schema.json` и
`manifest.json` пропускаются.

Проверено на 56 профилях: 48 `apache2handler` + 8 `fpm`. Все проходят
валидацию без ошибок и предупреждений (`cargo run -- profile validate`).

Особенности совместимости:

- `fixed_in` может быть `null` или произвольной строкой (например,
  `"none (EOL branch, no upstream fix)"`) — как в исходной схеме;
- `libphp.htdata` может отсутствовать или быть `null`;
- `stages` может быть пустым объектом;
- неизвестные поля сохраняются в `serde_json::Value` и попадают в экспорт;
- будущие значения `schema_version` дают предупреждение, но не блокируют
  чтение (compatibility mode).

## Контрольные суммы

`profiles/manifest.json` содержит SHA-256 для 106 файлов (профили, схемы,
offset-профили). Пути записаны относительно корня репозитория; загрузчик
поддерживает оба варианта (относительно `profiles/` и относительно корня).
Любое изменение исходного файла без обновления манифеста даёт предупреждение
при `profile validate` и проваливает compatibility-тест.

## Инвентарь

Колонки таблицы совпадают с оригиналом: `PHP, build, zif_system,
zval_ptr_dtor, htdata, stage1_n, forge, stage2_t, stage3, RCE`. В JSON
добавлены `status` и `file`, как и в `php2shell_inventory.py --json`.

## Реестр версий

Сохранены таблицы `FIXED` (8.2→8.2.35, 8.3→8.3.36, 8.4→8.4.27,
8.5→8.5.12) и EOL-ветки. Поведение `classify` совпадает с оригиналом:
строгий трёхкомпонентный parse, неизвестная ветка даёт `fixed=None`,
`patched=None`.

## Отчёты

Формат отчёта — `php2shell-rs/report/1.0`. Он включает версию
инструмента, режим, время, деперсонализированную цель, fingerprint,
диагностику и записи калибровки. Оригинальный `php2shell_assess.py --json`
использовал другие имена ключей (`php_version`, `sapi`, `pre_rinit_oom`,
`pointers`, `rce_confirmed`); прямой совместимости с ним нет, так как эти поля
описывали результат эксплуатации, который больше не производится.

## HTTP-фикстуры

Поддерживаются два формата: сырой HTTP-ответ (статус-строка, заголовки,
пустая строка, тело) и JSON `{url, status, headers, body}`. Специальный
заголовок `X-Observed-Url` подставляется в поле `target`.
